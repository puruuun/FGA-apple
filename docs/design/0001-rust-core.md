# 0001 Rust 코어와 Swift 껍데기로 iPhone 단독 주회 만들기

- 작성일: 2026-11-24
- 상태: **승인** (2026-11-24 소유자). 첫 목표의 범위와 작업 방식을 소유자가 정했습니다.
- 근거: [README](../../README.md)의 실측 결과, FGA-Modified의 `libautomata`·`scripts`, 그 저장소의 설계 0025(Rust 코어 단계적 전환)

## 1. 배경

검증 단계에서 확인된 것은 이렇습니다(수치는 README).

- ESP32가 블루투스 마우스로 붙어 탭·스와이프를 정확히 넣습니다.
- FGA의 템플릿과 좌표가 iPhone 화면에서 그대로 통합니다. PC 호스트(`host/`)가 FGA의 Kotlin 스크립트로 실제 주회를 끝까지 돌렸습니다.
- iPhone 앱이 뒤에 있는 동안에도 화면을 받고, 보드에 명령을 보내고, 메모리 600MB를 써도 종료되지 않습니다.
- 앱이 혼자서 화면을 보고 눌러 화면 사이를 왕복했습니다.

남은 것은 **게임 로직을 iPhone 안에서 돌리는 것**입니다. FGA의 로직은 Kotlin/JVM이라 iPhone에서 그대로 돌지 않습니다.

### 소유자 결정 (2026-11-24)

- FGA-apple의 로직은 **Rust로 새로 작성**합니다. FGA-Modified의 Kotlin 로직은 참고 자료이자 정답지로 씁니다.
- 앱의 껍데기는 Swift로 만듭니다.
- FGA-Modified는 Kotlin을 유지하면서 안 되는 부분만 Rust로 바꿔 가는 중이고, 로직 전체가 Rust로 갈지는 정해지지 않았습니다. 그래서 그쪽의 로직 이전을 기다리지 않습니다.

이 결정으로 **로직은 두 저장소에 따로 존재하게 됩니다.** FGA-Modified의 수정이 이쪽에 저절로 반영되지 않습니다. 이 문서의 5절(검증)과 6절(동기화)은 그 비용을 줄이기 위한 것입니다.

## 2. 목표와 비목표

**첫 목표: FGA의 전투 주회를 iPhone과 ESP32만으로 돌린다** (소유자 결정, 2026-11-24). 퀘스트를 출발해 원하는 서포트를 고르고, 스크립트대로 전투를 하고, 정해진 횟수만큼 반복하며, AP가 모자라면 설정대로 사과를 씁니다.

- 퀘스트 목록에서 퀘스트 선택
- AP 회복: 설정한 종류와 개수만큼 사과 사용, AP 자연 회복 대기. 설정에 없는 회복 수단은 쓰지 않음
- 지정 서포트 선택: 서번트, 예장, 친구, 클래스 탭, 최종 재림, 스킬 맥스 조건. 목록 스크롤과 갱신
- 파티 선택과 퀘스트 개시
- 스킬 커맨드 실행(대상 지정, 마스터 스킬, 오더 체인지 포함), 보구, 카드 선택(우선순위, 브레이브 체인)
- 결과 화면들 넘기기, 연속 출격, 실행 횟수 제한
- Android 앱에서 내보낸 전투 설정(`.fga`)을 그대로 읽기
- 앱에서 설정을 고르고 출발, 끝나면 알림

**비목표 (이 문서의 범위 밖. 뒤에 따로 다룹니다)**

- OCR이 필요한 조건(서포트 점수 +62, 그랜드 +16, 보구 레벨), 인연 추적
- 재료·예장 드롭 추적과 그에 따른 정지, 턴 제한 퇴각, 카드 수 기준 시작
- 스킬·어펜드 레벨업, 친구 포인트 소환과 매각, 예장 강화, 선물 상자, 복권
- 주간 미션 경로(두 손가락 동작이 필요), 로그 수집과 Chaldea 연동(Android 전용)
- iPad와 iPhone 17 이외의 기기, 세로 화면
- 특정 서버에서만 되는 기능. FGA-Modified에는 KR과 JP 전용 기능이 있지만 이쪽에는 들이지 않습니다

**서버:** 모든 서버를 지원합니다. 원본 FGA가 모든 서버에서 지원하는 기능만 옮기므로 서버별 차이는 템플릿 이미지뿐이고, 템플릿은 FGA의 규칙대로 서버 폴더에 없으면 En 것을 씁니다. 실기기 시험은 KR에서 합니다. 다른 서버는 실기기로 확인하지 못한 상태로 남습니다.

## 3. 구조

```
┌─ iPhone 앱 (Swift) ────────────────────────────────┐
│  화면 캡처 → 방향 판별·회전 → 프레임 제공            │
│  블루투스로 보드에 명령, 응답 대기                   │
│  설정 화면, 알림, 프레임 끊김 감시                   │
│        ▲ 프레임 요청 · 탭 요청 · 대기 · 알림         │
│        │ (UniFFI)                                   │
│  ┌─ Rust 코어 ───────────────────────────────────┐ │
│  │  scripts   전투·서포트 로직, 스킬 커맨드 해석    │ │
│  │  automata  영역·배율·대기·매칭 호출             │ │
│  │  vision    흑백 변환, 크기 조정, 템플릿 매칭     │ │
│  └───────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
        │ 블루투스 (HID 마우스 + 명령 서비스)
   ESP32 보드 (firmware/)
```

### 3.1 코어는 플랫폼을 모른다

코어는 아래 네 가지를 **플랫폼 인터페이스**로만 요청합니다. FGA의 `ScreenshotService`, `GestureService`, `Waiter`, `IScriptMessages`에 해당합니다.

| 요청 | iPhone 앱 | PC 실행기 | 재생 시험 |
| :--- | :--- | :--- | :--- |
| 화면 한 장 (바로 선 가로, 흑백 또는 컬러) | 캡처 프레임 | Mac 프레임 서버 | 녹화 파일 |
| 탭·스와이프 (끝날 때까지 기다림) | 블루투스 | USB 시리얼 | 기록만 함 |
| 대기, 현재 시각 | 실제 시간 | 실제 시간 | 가상 시계 |
| 알림·기록 | 앱 화면, 알림 | 콘솔 | 기록만 함 |

이렇게 하면 같은 코어를 세 곳에서 돌릴 수 있습니다. 특히 **PC 실행기**가 중요합니다. iPhone 앱을 만들기 전에, Rust 코어를 PC에서 돌려 실제 iPhone으로 주회를 돌려 볼 수 있습니다. 지금의 `host/`(Kotlin)와 같은 구성에서 로직만 Rust로 바뀐 것입니다. 앱 설치에는 사람 손이 필요하지만 PC 실행기는 그렇지 않아, 개발 중의 확인이 훨씬 빨라집니다.

### 3.2 로직은 FGA처럼 "기다리며 진행하는" 형태로 쓴다

FGA의 스크립트는 "이 그림이 보일 때까지 기다린다 → 누른다 → 사라질 때까지 기다린다"는 식으로 순서대로 쓰여 있습니다(`AutoBattle.loop`, `Region.exists(timeout)`, `waitVanish`). 코어도 같은 형태로 쓰고 전용 스레드에서 돌립니다.

- 이유: Kotlin 파일과 Rust 파일을 나란히 놓고 비교할 수 있어야 옮기기도, 나중에 FGA의 수정을 따라가기도 쉽습니다. "프레임을 받아 동작을 돌려주는" 상태 기계로 바꾸면 구조가 달라져 대조가 어려워집니다.
- 중지와 일시정지는 FGA의 `ExitManager`처럼 모든 대기·매칭·탭 지점에서 확인합니다.
- 재생 시험은 가상 시계로 해결합니다(5절).

### 3.3 Rust 크레이트

저장소의 `core/`에 Cargo 워크스페이스를 둡니다. 이름은 FGA의 모듈과 맞춥니다.

| 크레이트 | 대응하는 FGA 모듈 | 내용 |
| :--- | :--- | :--- |
| `vision` | `app/imaging/DroidCvPattern` | 이미지 타입, 흑백 변환, 크기 조정, 자르기, 템플릿 매칭(마스크 포함), 템플릿 읽기 |
| `automata` | `libautomata` | `Region`·`Location`·`Scale`·게임 영역, 플랫폼 인터페이스, `exists`·`waitVanish`·`click`·`wait`, 중지 처리 |
| `scripts` | `scripts` | 좌표(`locations`), 모델(스킬 커맨드, 카드 우선순위), 전투·서포트 모듈, 설정 읽기 |
| `ffi` | `native/fga-ffi` | UniFFI로 Swift에 내보내는 경계 |
| `cli` | `host/` | PC 실행기, 재생 시험 실행, 비교 도구 |

- `scripts` 안의 파일 이름과 배치는 Kotlin 쪽을 따릅니다(`modules/battle.rs` ↔ `modules/Battle.kt`).
- Rust 판과 도구 버전은 FGA-Modified의 `native/`에 맞춥니다(edition 2024). 나중에 `fga-sensing`을 가져다 쓸 때 어긋나지 않게 하기 위해서입니다.
- `unsafe`는 `ffi`와, 필요하다면 `vision`의 SIMD 부분에만 둡니다. 코어가 패닉하면 앱이 죽으므로 `unwrap`·`expect`는 테스트 밖에서 쓰지 않습니다(FGA-Modified의 Rust 규칙과 같음).

### 3.4 화면 처리

FGA는 화면을 높이 720으로 줄인 흑백에서 매칭하고, 좌표는 높이 1440 기준으로 적습니다. 코어도 같은 좌표 체계를 씁니다.

- **앱이 받는 화면:** 짧은 변 720으로 요청합니다(iPhone 17에서 720×1565). 형식은 `420f`라 밝기 평면을 그대로 흑백으로 씁니다. 컬러가 필요한 판별(`useColor`)에는 색 평면을 함께 변환합니다.
- **방향:** 가로 화면이 세로 버퍼 안에 시계 또는 반시계 방향으로 누워 들어옵니다. 앱이 방향을 정해 바로 세운 뒤 코어에 넘깁니다. 방향은 기기의 방향 알림으로 먼저 정하고, 매칭 점수로 확인합니다.
- **크기 조정의 차이:** FGA는 원본을 OpenCV의 `INTER_AREA`로 줄이고, 앱은 시스템이 줄여 준 화면을 받습니다. 검증에서 점수는 0.955와 0.969로 충분했습니다. 기준에 아슬아슬한 템플릿이 나오면 원본 해상도로 받아 코어에서 줄이는 방식으로 바꿉니다.
- **매칭:** `TM_CCOEFF_NORMED`와 같은 식을 `vision`에 구현합니다. 점수가 OpenCV와 ±0.01 안에 들어야 합니다(5절). FGA의 기준값을 그대로 쓰기 위한 조건입니다.

### 3.5 터치

- 좌표는 화면 픽셀에서 펌웨어 좌표(0..32767)로 바꿉니다. 화면 방향을 따라갑니다.
- **탭을 보낸 뒤에는 보드의 응답을 받고 나서 다음으로 넘어갑니다.** 응답 전에 화면을 다시 보면 같은 탭을 또 보내게 됩니다(검증에서 실제로 겪음).
- 누를 수 없는 세로 띠는 기기와 방향별 값을 앱이 갖고 보드에 설정합니다. 값이 없는 기기·방향에서는 시작을 막습니다.
- 두 손가락 동작은 없습니다.

### 3.6 안전 규칙

검증에서 얻은 것들이고, 코어와 앱이 반드시 지킵니다.

1. 앱 자신이 화면에 떠 있는 동안에는 탭을 보내지 않는다.
2. FGO의 아는 화면으로 확인될 때만 누른다. 모르는 화면에서는 기다린다.
3. 프레임이 일정 시간 들어오지 않으면 멈추고 알린다. iOS는 캡처가 끊겨도 알려 주지 않는다.
4. 보드 응답이 제한 시간 안에 없으면 멈추고 알린다.
5. AP 회복 아이템과 성정석은 설정에서 명시적으로 허용한 경우에만 쓴다. 기본은 쓰지 않는다.
6. 화면 캡처 이미지는 저장소에 넣지 않는다. 계정 정보가 찍힌다.

### 3.7 설정

- Android 앱에서 내보낸 전투 설정(`.fga`)을 그대로 읽습니다. 키 이름과 기본값은 FGA-Modified의 `prefs` 모듈과 같게 합니다. `host/`의 `KvStore`·`HostBattleConfig`가 이미 그렇게 하고 있어 그대로 옮깁니다.
- 서포트 이미지는 FGA-Modified에 내장된 것을 앱에 넣고, 사용자가 추가한 것을 함께 읽습니다.

## 4. 단계

각 단계는 완료 기준을 만족해야 끝난 것으로 봅니다.

| 단계 | 내용 | 완료 기준 |
| :--- | :--- | :--- |
| **M0 준비** | Cargo 워크스페이스, CI(`cargo fmt`·`clippy`·`test`), PC 호스트(Kotlin)에 녹화 기능, 정답 내보내기 도구 | CI가 통과. 호스트로 주회 한 판을 녹화한 파일이 재생 가능한 형식으로 남음 |
| **M1 vision** | 이미지 타입, 흑백·크기 조정·자르기, 매칭(마스크 포함), 템플릿 읽기 | 녹화 프레임에서 OpenCV와의 점수 차가 ±0.01 이내. 1565×720에서 300×120 영역 매칭이 iPhone 기준 10ms 이내 |
| **M2 automata + 좌표 + 설정** | `Region`·`Scale`·게임 영역, 플랫폼 인터페이스, `exists`·`waitVanish`·`click`, 좌표, `.fga` 읽기 | 좌표가 Kotlin이 내보낸 정답과 화면 크기 5종 이상에서 완전히 일치. 설정이 호스트가 읽은 값과 일치 |
| **M3 모델** | 스킬 커맨드 해석, 카드 우선순위, 브레이브 체인, 전투 상태 | 해당 Kotlin 테스트의 입력과 기대값을 옮긴 테스트가 통과 |
| **M4 전투 흐름** | `AutoBattle` 루프(첫 목표 범위), 전투, 서포트 선택, PC 실행기 | 녹화 재생에서 Kotlin과 같은 동작 순서. PC 실행기로 실제 iPhone에서 11-23의 두 설정이 정상 종료 |
| **M5 iPhone 앱** | `ffi`, Swift 껍데기(캡처, 방향, 보드, 설정 화면, 알림, 감시) | iPhone과 ESP32만으로 11-23의 두 설정이 정상 종료 |
| **M6 다지기** | 연속 실행, 중단 상황(잠금, 전화, 알림), 장시간, 사과 사용 | 3시간 연속 주회가 사람 손 없이 끝남. 중단 상황마다 정해진 대로 멈추거나 이어 감 |

M1, M2, M3은 서로 의존하지 않아 동시에 진행할 수 있습니다. M5의 Swift 껍데기 중 코어와 무관한 부분(캡처, 방향, 보드 연결)도 검증 앱(`ios/FGAProbe`)을 바탕으로 처음부터 함께 진행할 수 있습니다. M4는 M1~M3이 끝나야 시작합니다.

**M6 이후:** OCR(FGA-Modified의 `fga-sensing`을 커밋을 고정해 가져옴. 순수 Rust 추론 엔진인 tract를 쓰면 iPhone용으로 빌드될 것으로 보지만 확인 전), 비목표로 미룬 기능들, 다른 기기.

## 5. 검증

로직을 새로 쓰는 계획의 가장 큰 위험은 "원본과 미묘하게 다르게 동작하는 것"입니다. 네 겹으로 막습니다.

1. **옮긴 테스트.** FGA-Modified의 `scripts`에는 테스트가 137개 파일, 약 22,000줄 있습니다. 첫 목표 범위에 해당하는 테스트(스킬 커맨드, 카드 우선순위, 직접 카드 지정, 전투 흐름 등)의 입력과 기대값을 Rust 테스트로 옮깁니다.
2. **정답 비교.** PC 호스트가 Kotlin 코드를 실행해 정답을 내보내고, Rust의 결과와 비교합니다.
   - 좌표: 화면 크기별 모든 좌표와 영역
   - 매칭: 녹화 프레임 × 템플릿의 OpenCV 점수
   - 설정: `.fga`를 읽은 결과
3. **녹화 재생.** PC 호스트로 주회를 돌리며 화면 흐름(시각 포함)과 Kotlin이 한 동작을 녹화합니다. Rust 코어에 가상 시계와 함께 같은 화면 흐름을 주고, 동작의 순서와 대상이 같은지 봅니다. 시각까지 같을 필요는 없습니다. 재생은 화면이 코어의 탭에 반응하지 않으므로, 동작이 갈라진 지점부터는 비교하지 않고 그 지점을 보고합니다.
4. **실기기.** PC 실행기로, 그다음 iPhone 앱으로 실제 주회를 돌립니다. 사람이 지켜보는 상태에서, 사과를 쓰지 않는 설정으로, 횟수를 제한해 시작합니다.

1~3은 게임과 기기 없이 CI에서 돕니다. 녹화 파일에는 계정 화면이 들어 있어 저장소에 넣지 않고, CI에서는 계정 정보가 없는 작은 견본만 씁니다(견본을 어떻게 만들지는 M0에서 정함).

## 6. FGA-Modified와의 동기화

- **템플릿 이미지:** 서브모듈에서 그대로 가져옵니다. 따로 관리하지 않습니다.
- **좌표와 기준값:** Rust로 옮겨 적되, 5절의 정답 비교가 지킵니다. 서브모듈을 올린 뒤 정답을 다시 내보내면, FGA-Modified에서 바뀐 좌표는 Rust 테스트의 실패로 드러납니다. 실패한 곳을 고치면 동기화가 끝납니다.
- **로직:** 서브모듈을 올릴 때 첫 목표 범위 파일들의 변경 내역을 읽고 Rust에 반영합니다. 파일 이름이 대응되므로 어디를 봐야 할지는 분명합니다. 녹화 재생이 놓친 차이를 잡습니다.
- **OCR 엔진:** FGA-Modified의 `fga-sensing`을 복사하지 않고 의존성으로 가져옵니다.

앞서 "좌표를 파일로 내보내 Rust가 읽게 한다"는 안을 말씀드렸는데, 이 문서에서는 **좌표를 Rust로 옮기고 내보낸 값은 시험의 정답으로만 쓰는 것**으로 바꿨습니다. 내보낸 파일을 실행 중에 읽게 하면 새 기기나 화면 크기마다 PC에서 파일을 다시 만들어야 해서, iPhone만으로 쓴다는 목표와 맞지 않습니다.

## 7. 작업 방식

변경은 브랜치와 PR로 하고, CI가 통과해야 `main`에 합칩니다. 모든 에이전트가 지킬 규칙은 저장소의 [AGENTS.md](../../AGENTS.md)에 있습니다. 작업을 어떻게 나누고 누구에게 맡기는지는 기획자가 정하며 이 저장소에 적지 않습니다.

기기와 게임을 쓰는 시험, Xcode 서명과 설치는 소유자와 기획자만 합니다.

### 7.1 CI (GitHub Actions)

PR마다 돌리고, 통과해야 `main`에 합칩니다. 바뀐 폴더에 해당하는 검사만 돌립니다.

**지금 저장소에 있는 것에 대한 검사**

| 검사 | 내용 | 실행 환경 |
| :--- | :--- | :--- |
| 호스트 빌드 | 서브모듈을 받아 `./gradlew :host:compileKotlin`. 서브모듈을 올렸을 때 FGA 쪽 변경으로 호스트가 깨지는 것을 잡습니다 | Linux, JDK 21 |
| 펌웨어 빌드 | `pio run -d firmware`로 두 보드 설정 모두 | Linux |
| iPhone 앱 빌드 | 서명 없이 `xcodebuild build`. 프로젝트 파일에 소스가 빠지는 실수를 잡습니다 | macOS. 러너의 Xcode가 iOS 27 SDK를 갖고 있어야 하므로, 안 되면 Mac에서 수동 확인으로 둡니다 |
| Python 도구 | 문법 검사와 린트 | Linux |
| 저장소 위생 | 올라가면 안 되는 것이 섞였는지: 이미지와 녹화 파일, 내보낸 전투 설정(`.fga`), 프로젝트 파일의 서명 팀, 사설 IP 주소, 비밀 값 | Linux |
| 서브모듈 | `fga`가 가리키는 커밋이 FGA-Modified 원격에 실제로 있는지 | Linux |

**Rust 코어가 생기면(M0) 추가하는 검사**

| 검사 | 내용 |
| :--- | :--- |
| 형식과 린트 | `cargo fmt --check`, `cargo clippy -- -D warnings` |
| 테스트 | `cargo test` (옮긴 테스트, 정답 비교, 견본 녹화 재생) |
| iPhone용 컴파일 | `cargo check --target aarch64-apple-ios`. PC에서만 되는 코드가 코어에 섞이는 것을 잡습니다 |
| 의존성 | `cargo deny`로 라이선스와 알려진 취약점 확인 (FGA-Modified와 같은 방식) |
| 정답의 신선도 | 서브모듈이 바뀐 PR에서는 Kotlin으로 정답을 다시 내보내 저장된 것과 같은지 확인. 다르면 좌표나 기준값이 FGA 쪽에서 바뀐 것 |

**CI가 하지 않는 것:** 기기와 게임을 쓰는 시험, 서명과 설치. 실제 계정 화면이 담긴 녹화는 CI에 올리지 않습니다.

## 8. 위험

| 위험 | 대응 |
| :--- | :--- |
| Rust 로직이 Kotlin과 미묘하게 다르게 동작 | 5절의 네 겹 검증 |
| 매칭 점수가 OpenCV와 달라 기준값이 맞지 않음 | M1의 완료 기준(±0.01). 안 되면 `vision`의 매칭만 OpenCV로 교체 |
| 범위가 불어나 첫 목표가 늦어짐 | 2절의 비목표를 지킴. 추가는 M5 이후 |
| FGA-Modified의 변경을 따라가지 못함 | 6절. 서브모듈을 올릴 때마다 정답을 다시 내보냄 |
| iOS 업데이트로 캡처·포인터 동작이 바뀜 | 검증 앱(`ios/FGAProbe`)을 유지해 업데이트 뒤 다시 측정 |
| 화면 잠금·전화 등으로 캡처가 끊김 | 3.6의 감시. 세부 동작은 M6에서 측정 후 정함 |
| 무료 계정의 7일 재서명과 3개 제한 | 개발 중에는 감수. 배포 방식은 M6 이후 따로 정함 |
